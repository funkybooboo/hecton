# v0.2.0 - First live session + market-verified tiers

All prices and model sizes in this plan were verified live on 2026-10-01
(vast.ai public offers API, ollama library pages, HuggingFace file trees).
Answers to the v0.1.0 open questions landed 2026-10-01: monorepo confirmed,
flat kebab-case commands (`/hecton-up`, `/hecton-down`, ...), Docker Hub image
stays `natestott/hecton-server`, defaults re-picked from the live market,
vast.ai account + API key created by the user.

## What the live research changed (big findings)

1. **No H100s exist on the market anymore.** The idea.md premise ("rent H100
   spot") is stale; the 2026 market is Blackwell/Ampere. Defaults moved to
   RTX PRO 6000 Max-Q (96GB, $0.64/hr cheapest observed). The repo name
   "hecton" stays (an H100 homage).
2. **Offer search is a public API** and the query format was reverse-engineered
   from validation errors: operator dicts + order tuples. The client now uses
   the VERIFIED format; `/hecton-check` works before any key is configured.
3. **glm-5.3 has no pullable weights in the ollama registry** (only a
   `:cloud` tag) - that is ollama's cloud lock, not missing weights:
   `unsloth/GLM-5.3-GGUF` on HuggingFace is open (597k downloads). Same for
   kimi-k3, minimax-m3, mistral-large-3, glm-5.3-flash, nemotron-3-ultra:
   all `:cloud`-only in the registry, all open on HF. Hecton's frontier tier
   serves real GLM-5.3 via HF GGUF imports (`hf.co/...` tags work in ollama).
4. **GLM-5.3 is ~755B params**: unsloth quant sizes are IQ3_XXS 282GB,
   IQ4_XS 365GB, Q4_K_XL 467GB. GLM-5.3-Flash (~320B): Q3_K_XL 148GB,
   IQ4_XS 157GB, Q4_K_XL 200GB.

Notes:
- GLM-5.3-Flash IQ4_XS on 2x Max-Q ($1.27/hr) is the sweet spot: real GLM
  quality for ~$147/mo at full usage. That is the recommended target tier.
- qwen3-coder:480b-a35b-q4 (290GB, biggest open coder in the ollama
  registry) also fits the 4x tiers if preferred over GLM.
- KV cache headroom per tier: budget 31GB, workhorse 15GB,
  daily-driver-alt 35GB, frontier-alt 38GB. Context windows must be set
  per model in config accordingly (start 64k-128k, measure).
- Token/s estimates (active params x bandwidth, rough): Flash ~18-30B active
  on 2x Blackwell = 40-80 tok/s; GLM-5.3 on 4x = 20-40 tok/s. Measure in
  v0.3.0; idea.md's "match ollama cloud ~95 tok/s" is only reachable on the
  small-active-param tiers.

## Milestone v0.2.0 - first live session (runbook)

Goal: prove the whole pipeline once, cheaply, then destroy.

0. User setup (one-time):
   - vast.ai account with ~$5 credit; API key created.
   - SSH public key uploaded to vast.ai console (settings -> SSH keys).
   - Key placed at `~/.pi/agent/hecton/.env` as `VAST_API_KEY=...`
     (chmod 600; alternatively export it or use hecton.json apiKey).
   - `docker login` (for pushing natestott/hecton-server).
1. Build + CPU smoke test the server image locally (server/README.md),
   push to Docker Hub.
2. `/hecton-check` - key auth check via instances list (read-only) + market.
3. `/hecton-up` with default models (qwen3-coder:30b + gpt-oss:20b, ~33GB
   total pull) on the default 1x Max-Q config; expect ~$0.65/hr.
   - Fix any create/list field drift (docs/vast-api-notes.md lists what
     is still assumed; VastApiError carries raw bodies).
4. `/hecton-connect`; verify SSH/tunnel; if SSH fails, debug with a manual
   `ssh -p <port> root@<ip>`.
5. `/model hecton:qwen3-coder:30b` - first end-to-end completion through
   the rented GPU. Also `/hecton-models pull gpt-oss:120b` to exercise the
   pull path (65GB; skip if slow).
6. `/hecton-down` - destroy, confirm billing stopped in the vast.ai console,
   reconcile recorded cost vs the console's charge.
7. Commit fixes, update this plan with what was learned, push.

Risks for the runbook:
- create/destroy endpoint drift (fallback: vastai CLI, or fix paths from
  error bodies - the client surfaces them).
- sshd-in-image question (hecton-server starts it best-effort; if vast
  provisions SSH differently, drop openssh-server from the image).
- ollama `hf.co/<user>/<model>:<quant>` pulls (tier models) - VERIFY one
  works during v0.2.0 (multi-file/sharded GGUF support is the specific
  risk for the 157GB+ quant dirs; if ollama chokes on shards, fallback is
  pre-merged single-file GGUFs or llama.cpp serve, decided in v0.3.0).

   "RTX PRO 6000 Max-Q", diskGb 300, cap $1.60/hr, models:
   GLM-5.3-Flash via `hf.co/unsloth/GLM-5.3-Flash-GGUF:UD-IQ4_XS`.

   context lengths; tune contextWindow in config to fit KV cache.

   `/hecton-up` -> relaunch, measure total downtime (target < 15 min).

   type) for cheaper rates with spot preemption - add config knob
   `bidDiscount` and measure win rate over a week.
5. Idle-cost guard: footer timer + optional auto-down after N idle hours
   (protects the "left it running overnight" case).

## Decisions added in v0.2.0

- D7: flat kebab-case commands (pi-idiomatic; matches pi's own extension
  examples like builtin-header, status-card). No subcommand dispatcher.
- D8: default hardware target = RTX PRO 6000 Max-Q 96GB (Blackwell) at a
  $1.20/hr cap; A800 80GB is the budget alternative at $0.47/hr.
- D9: frontier models come from HuggingFace GGUF imports (unsloth quants),
  since the ollama registry gates glm/kimi/minimax/mistral behind `:cloud`.
- D10: the API key lives at `~/.pi/agent/hecton/.env` (VAST_API_KEY=...),
  chmod 600, outside any repo; pi does not auto-load .env files so the
  extension parses this one itself. Env var and hecton.json apiKey still
  work (priority: env var > .env > config json).
