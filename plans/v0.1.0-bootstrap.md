# v0.1.0 - Bootstrap

## What hecton is

Hecton gives you the "Ollama Cloud" experience on GPUs you rent by the hour.
One command inside pi (`/hecton-up`) finds the cheapest Vast.ai spot H100 under a
price cap, launches it with an Ollama server image, tunnels it to
`127.0.0.1:11435`, and exposes the remote models as a normal pi provider so
`/model` just works. `/hecton-down` destroys the instance and reports the cost.

Origin: the hardware research saved in `idea.md` (Mac Studio vs renting vs
providers). Conclusion there: spot-renting H100s at ~116 hrs/month usage
(weekday evenings 2-4h, weekends 4-8h/day) costs ~$140-280/month versus
$12k+ up front for hardware, and the user prefers smartest-model-over-speed
and cheapest-with-automation.

## Components

- `server/` - Docker image pushed to Docker Hub; runs ON the Vast.ai instance.
  Base `ollama/ollama`, entrypoint starts sshd (Vast SSH access), `ollama serve`,
  pre-pulls models from `HECTON_MODELS` env, graceful SIGTERM trap.
- `extensions/hecton/` - pi extension (the local product). Pure TypeScript,
  Node builtins only, no runtime deps. Commands: `/hecton-up|down|status|connect|
  check|cost|models`. Registers pi provider `hecton` -> OpenAI-compat
  `http://127.0.0.1:11435/v1`.

## Decisions

- D1: Monorepo. The conversation in idea.md proposed two repos, but one repo
  works: `pi install git:github.com/funkybooboo/hecton` clones this repo and
  conventional `extensions/` discovery loads the extension. The server image is
  built/pushed from `server/` separately.
- D2: Pure-TS Vast.ai REST client (no `vastai` Python CLI dependency). Keeps
  this machine's declarative NixOS setup untouched (no new system packages);
  the extension is fully self-contained. The official CLI remains a fallback
  driver if REST shapes have drifted (see docs/vast-api-notes.md).
- D3: Tunnel binds `127.0.0.1:11435`, NOT 11434. A local Ollama daemon can keep
  using 11434 simultaneously; provider id `hecton` never collides with the user's
  existing `ollama` provider in models.json.
- D4: Provider registration happens in the extension factory (async), probing
  the tunnel for a live model list with a config-defined fallback. pi flushes
  registerProvider calls before startup, so `/model` and `--list-models` see
  it. Model list refreshes on pi restart or `/reload` after a pull.
- D5: No server-side checkpoint daemon. pi persists sessions locally; the
  instance is stateless and disposable. Resilience = fast `/hecton-up` relaunch +
  instance record kept in `~/.pi/agent/hecton/state.json`. The idea.md
  checkpoint.py system is intentionally dropped.
- D6: Model list and GPU target are config (`~/.pi/agent/hecton.json`), never
  hardcoded. Defaults ship real, modest ollama tags that fit 1xH100 80GB.

## Corrections vs idea.md (recorded so we do not relitigate)

- The pi extension API in idea.md is fictional. Real API: `pi.registerCommand`,
  `pi.registerProvider`, `pi.on`, `ctx.ui.notify/confirm/select/setStatus/
  setWidget`, `ctx.hasUI`. pi already speaks Ollama via models.json patterns,
  so no custom streaming code is needed at all.
- Model size contradiction: idea.md says GLM-class Q4 is ~75GB (fits 1xH100)
  AND ~220GB+ (does not). Reality: 1xH100 80GB fits ~30B fp16 or ~120B-class
  q4; glm-5.3-class ~753B models at q4 (~220GB+) need 3-4x H100 80GB or
  2x H200 141GB (Ollama splits layers across GPUs). Hence tiers.
- "GLM 5.3" is real and already served by the user's ollama-cloud provider
  (confirmed via pi --list-models: glm-5.3, 1M context). The point of
  hecton is running that class of model on rented GPUs instead of paying
  the cloud; the frontier tier therefore means a multi-GPU instance, not a
  single H100. Defaults ship smaller real tags that fit 1xH100 so the first
  live session is cheap.
- Vast.ai REST endpoints (v0: `/api/v0/bundles`, `/api/v0/asks/{id}/`,
  `/api/v0/instances/`) are written from training knowledge, NOT verified.
  v0.2.0 verifies with read-only calls first. Fallback: shell out to the
  official `vastai` CLI.

## Roadmap

- v0.1.0 (this) - bootstrap: repo skeleton, plan, server image, extension with
  all commands implemented against the real pi API, unit tests for pure logic,
  extension smoke-tested loading under pi. No live Vast.ai calls yet.
- v0.2.0 - first live session (needs the user's vast.ai account + API key +
  SSH pubkey registered): verify auth, offer search shapes, create/destroy,
  sshd behavior, tunnel, first GPU session with a real model. Fix drift found
  in docs/vast-api-notes.md. Push server image to Docker Hub.
- v0.3.0 - resilience and cost polish: spot-interruption detection and quick
  relaunch, monthly cost ledger report, footer status updates, `models pull`
  verification on a live GPU, idle-timeout reminder.
- v0.4.0 - model tiers: named tiers (workhorse 1xH100 80GB vs frontier
  3-4xH100 / 2xH200 for glm-5.3-class ~753B models) with per-tier model lists
  and budget caps; optional vLLM image variant for multi-GPU tensor
  parallel speed.
